Coord Architecture

One language, TypeScript, from the browser to the database. The app paints from a local copy first, so it feels instant, then checks with the server. Postgres keeps each studio's data walled off from every other studio.

The system at a glance

Three layers plus one shared package. Solid boxes exist today; dashed boxes arrive in later milestones.

Language

TypeScript everywhere

  • The pricing math, the role rules and the form checks are written once and run in the browser and on the server. An item's price in the editor matches the saved price exactly.
  • Changing a field's type updates every screen and route at compile time, so mistakes show up before release.
  • One language keeps a small team fast, and UX work needs fast iteration.
Why not Rust

The server isn't where time goes

On a request that does reach the server, our code is a sliver of the wait. Rust would shrink that sliver; the network and the database would not change.

What happens when a designer changes an item

Example: Priya, an assistant, changes the quantity on the Henderson sofa.

  1. The row updates the moment she types. The app changes its local copy first and shows it.
    Browser · TanStack Query optimistic update
  2. The change goes to the server. A small JSON request with her session cookie.
    Browser → API · PATCH /api/items/:id
  3. The server checks who she is and what she may do. The cookie is matched against a stored hash, the origin is checked, and her role must allow editing projects.
    API · session, CSRF and permission check
  4. The database only shows her own studio. The query runs as a restricted role scoped to Hollis Interiors, so another studio's rows can't be reached even by a bug.
    Postgres · row-level security
  5. The reply leaves out what she can't see. Assistants don't see cost or margin, so those fields are removed before the response is sent.
    API · cost-hiding serializer
  6. Everyone else's screen catches up. The server announces which data changed. Maya's open browser refetches the sofa and its totals within a second.
    API → browsers · NOTIFY, then Server-Sent Events
  7. Next visit opens instantly. The fresh data is saved in the browser, so the project paints before the network answers.
    Browser · IndexedDB copy

Where it runs

The same code runs on a laptop with no setup and on Vercel with a hosted database. Only the connection string changes.

On your laptop · npm run dev
  • Web at localhost:5173. Vite reloads on save and forwards /api to the API.
  • API at localhost:8790, run with tsx.
  • Database: PGlite, real Postgres compiled to run inside Node. Files sit in apps/api/.data. Nothing to install.
  • Live updates and the server cache run in memory.
  • npm run seed resets it to the sample studios.
Live · Vercel
  • Web: static files on Vercel's CDN. File names are hashed, so they're cached forever.
  • API: one Node function that handles every /api request.
  • Database: Neon or Supabase Postgres through DATABASE_URL.
  • Live updates go through Postgres LISTEN/NOTIFY, because function instances don't share memory. The server cache is off; the browser copy does that job.

How it's built and checked

Repository

coord/
├─ packages/shared   # pricing, roles, schemas, types
├─ apps/web          # React app
│  └─ src/pages, data, ui
├─ apps/api          # Hono API
│  └─ src/routes, db, catalog
├─ scripts           # Vercel build, size budget
├─ vercel.json
└─ .github/workflows/ci.yml

npm workspaces link the three packages. Shared code is imported as TypeScript source, with no build step of its own.

Every push · npm run ci

typecheck→58 tests→build→size budget
  • Tests cover pricing cases, role rules, studio isolation, cost hiding, link clipping and CSV import.
  • The budget fails the build if the first download passes 200 KB of JavaScript or 30 KB of CSS. Today: 149 KB and 6 KB.

Deploy · npm run build:vercel

vite build→migrate DB→esbuild API→.vercel/output

Migrations run during the build, not when a function starts, so two instances never race to change the schema.
