# 0.2: Money kernel

> Status: **Built** (2026-11-03)
> Money gate: **yes** · Native app: yes (the same package runs on the phone)

## Why

Every dollar Coord shows or charges passes through this one small package. The old app multiplied
money by fractional numbers and got real cases wrong ($102.50 at 15% markup gave $117.87 instead
of $117.88). This slice builds the arithmetic once, exactly, and proves it before any feature uses
it. It also turns the money policy into code, so the rules you approve are the rules that run.

## In scope

1. **`docs/money-policy.md`** approved by you, including decisions **D-1** (deposit base) and
   **D-2** (freight differences). Approved.
2. **`packages/money`**, a dependency-free package used by the API, web and phone:
   - **Types** that can't be mixed up: `Cents`, `Rate` (parts per million), `Quantity`
     (thousandths), `Seconds`. Passing a rate where cents are expected is a type error.
   - **One core operation**, `multiplyAndDivide(a, b, divisor)`, exact for any size (whole-number
     math with no rounding until the end), then rounded half away from zero.
   - Built on it: `applyRate` (8.25% of an amount), `multiplyByQuantity` (2.3 yd × $1.05),
     `sum` (with overflow checks), `split` (largest-remainder allocation).
   - **Parsing** for money, rates, quantities and durations, returning either a value or a
     plain-language reason ("Use at most two decimals").
   - **Formatting** for the same four kinds, US style.
3. **Pattern registry entry** for money arithmetic, parsing and formatting.

## Out of scope

- **Pricing formulas** (markup, margin, MSRP discount, COM components). They belong in
  `packages/domain` and come with items in C2, built on this kernel.
- Tax, deposit and time **rules for documents**. Those apply the policy to proposals and invoices
  in D1 and G3; this slice provides the exact arithmetic they use.
- Input components such as `MoneyInput`. Those come in 0.6, built on these parsers.

functions. A timer total on the phone and on the web can never differ.

## Test plan (the accuracy gate)

1. **Golden fixture table** (`fixtures.ts`): every example in the money policy, every bug found
   in the old app ($102.50 at 15%, $102.45 less 30%, 2.3 yd at $1.05, 8.875% tax), and edge cases
   (zero, one cent, largest allowed amount, negatives).
2. **Property tests** (fast-check, thousands of random cases each), checked against an
   independent reference written with fractions:
   - every result is a whole number of cents and within the allowed range;
   - exact halves always round away from zero; credits mirror charges;
   - `split` always adds up to the total, never gives a line more than its share plus one cent,
     and is the same every time;
   - `format(parse(x))` returns the same text for any valid amount.
3. **Parser table**: every accepted and rejected input in the policy, plus tricky ones (`1e3`,
   `0x10`, `1.250,00`, `12.345`, `--5`, whitespace, full-width digits).
4. **100% branch coverage** (already enforced by CI from 0.1).
5. **Mutation testing** with Stryker: the tool deliberately breaks the code in hundreds of small
   ways (flip `<` to `<=`, change a rounding direction) and every break must make a test fail.
   Target: **100% on this package**; CI fails below 95%.

## Demo script

1. Open `docs/money-policy.md`; the two decisions show your answers.
2. Run `npm run ci`: green, and the coverage report shows 100% for `packages/money`.
3. Run `npm run mutation`: the report shows every injected bug was caught.
4. I walk you through `multiplyAndDivide` and `split` (short, commented functions) and the
   fixture table, including the old app's wrong answers next to the right ones.
